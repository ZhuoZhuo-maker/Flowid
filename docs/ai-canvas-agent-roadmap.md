# Flowid 画布 AI 代理（云端模型 + 工具）实施路标

本文档说明：**在预设模板与系统提示词尚未完善时，应先完成什么**；之后如何分阶段把「对话 → 调画布 / 提示词 / 工作流」做成可产品化的能力；每一阶段建议的 **工具（Tools）数量**；以及 **Skill 能否替代你自己设计工具**。

---

## 0. 前置条件：为什么必须先完善「预设模板」和「系统提示词」

画布 AI 代理的本质是：**模型在「可控的动作空间」里做决策**。这个动作空间依赖两类「人类已整理好的资产」：

| 资产 | 作用 |
|------|------|
| **系统提示词** | 定义风格、角色、输出格式、合规边界；可被代理「选用」或注入到节点。 |
| **预设模板** | 定义可复用的节点组合 / 工作流片段；代理通过「合并模板」快速搭出正确拓扑。 |

若二者不完善，会出现：

- 模型**不知道**有哪些「官方可选能力」，只能瞎编节点名或虚构预设名。
- 即使用 **Skill** 写好说明书，也没有**稳定、可枚举**的目录给模型引用，Skill 里只能写空话。

**结论：**  
**建议顺序：** ① 系统提示词与预设模板的「命名、分类、描述、可发现性」到位 → ② 再在应用内接工具与多轮对话。**  
你可以在并行做小工具原型，但**不要**把大量精力花在「全量工具」上，直到目录与元数据稳定。

---

## 1. Skill 能不能让你「不用自己想工具」？

**不能替代。** 需要分清三层：

| 层级 | 是什么 | 谁来做 |
|------|--------|--------|
| **Tools（工具）** | 程序真实能执行的能力：读节点、改字段、合并模板、触发 Comfy 等。**必须对接你的代码与数据。** | **必须由你（或团队）定义并实现。** |
| **Skills（技能）** | 给模型的**说明书 + 流程套路**：何时用哪些工具、示例对话、边界与纠错。类似「岗位手册」。 | 可自建；也可用社区 OpenClaw/ClawHub 类 **Skill 当参考**，但 **执行体仍须映射到你的 Tools**。 |
| **模型** | 在 Tools + Skill + 用户话的前提下推理与调用。 | 选云端强工具调用模型。 |

**Skill 能帮你省掉的是：**

- 大量「教模型怎么说」的 **prompt 工程**与 **SOP 文档化**；
- 一些 **通用套路**（例如「先列节点再改再执行」）的文字模板。

**Skill 不能省掉的是：**

- **每个 Tool 的入参/出参、权限、错误码**；
- **与 Flowid 画布、执行引擎、磁盘工程的真实绑定**。

若未来接 **OpenClaw** 等外部代理：OpenClaw 的 Skill 仍然要通过 **HTTP/CLI 等**调用你暴露的接口——**接口本身就是 Tools 的对外形态**。

**一句话：**  
**Skill = 说明书与编排；Tool = 手脚。没有手脚，说明书无法落地。**

## 2. 总览：阶段与建议工具数量

以下为 **在应用内自建「云端模型 + Tools」** 的路线（与是否使用 OpenClaw 外挂无关；外挂阶段更晚）。

| 阶段 | 名称 | 建议 Tool 数量 | 说明 |
|------|------|----------------|------|
| A | 资产与目录就绪 | **0**（不写执行工具） | 预设模板 + 系统提示词可检索、描述一致。 |
| B | 工具骨架 + 云模型打通 | **2～3** | 只证明「多轮 + tool 执行」闭环。 |
| C | 画布读写 v1 | **+4～6**（累计约 **6～9**） | 读节点、改提示词、连线、执行等。 |
| D | 资产类工具 | **+3～5**（累计约 **9～14**） | 应用系统提示词预设、合并预设模板、列目录。 |
| E | 工作流 / Comfy | **+4～8**（累计约 **13～22**） | 绑定工作流、设参、跑图、取状态/结果摘要。 |
| F | 风控、观测、成本 | 不增或 **+1～3** | 确认、审计日志、限流等。 |

**工具数量原则：**  
- **宁少勿滥**：每个 Tool 职责单一、可测、可文档化。  
- **合并诱惑要克制**：「万能 run」类 Tool 往往难调试，后期再考虑高层封装。

## 3. 各阶段详细说明

### 阶段 A：资产与目录就绪（Tool：0）

**目标：** 模型和人类都能一眼知道「有什么可选用」。

**要做的事：**

1. **系统提示词**
   - 每条有稳定 **标题**（与磁盘/索引键一致）、**短描述**、**分类**（如剧本 / 生图）。
   - 有一份 **机器可读清单**（JSON 或生成脚本）：`id / title / category / one_line_purpose`。

2. **预设模板**
   - 每条有稳定 **名称**、**分类**、**tier**、**一句话说明**（给模型用）。
   - 与封面、合并行为一致；避免同名歧义。

3. **验收**
   - 任意一条预设/提示词，人能 **10 秒内**在 UI 里找到并理解用途。

**产出物：** `prompts-catalog.json` / `templates-catalog.json`（名称可自定），后续 Tool「列目录」直接读。

---

### 阶段 B：工具骨架 + 云端模型（Tool：2～3）

**目标：** 不依赖完整资产，先证明 **Chat Completions + tools + 多轮** 在 Flowid 里跑得通。

**建议 Tool 示例（2～3 个）：**

| # | Tool 名（示例） | 作用 |
|---|-----------------|------|
| 1 | `ping_canvas` | 返回当前工程名、节点数量（证明链路与权限）。 |
| 2 | `echo_user_intent` | 把用户目标结构化摘要（调模型自律，可选）。 |
| 3 | `append_system_message` | 仅往助手对话里追加一条系统可见信息（调试用，可选）。 |

**验收：** 用户一句话 → 模型发 tool call → 前端执行 → 结果回注 → 模型用自然语言总结；**全程可打日志**。

---

### 阶段 C：画布读写 v1（本阶段新增约 4～6 个，累计约 6～9）

**目标：** 代理能完成「最小有用」的画布操作。

**建议 Tool：**

| # | Tool（示例） | 说明 |
|---|--------------|------|
| 1 | `list_nodes` | 返回 id、类型、标题、关键字段摘要（控制 token）。 |
| 2 | `get_node` | 按 id 取详情（可选与 list 合并策略）。 |
| 3 | `update_node_prompt` | 按节点类型写「主提示词」字段（需白名单字段）。 |
| 4 | `create_node` | 与现有能力对齐，参数 kind + 初始标题/位置。 |
| 5 | `connect_nodes` | source/target 明确（id 或稳定标题查询）。 |
| 6 | `run_nodes` | 执行指定节点或当前选中（与现有执行栈对齐）。 |

**验收：** 固定 **10 条**用户话术（阶段 0 写的用例），每条 **≤5 轮 tool** 内完成且画布可人工核对。

---

### 阶段 D：资产类工具（本阶段新增约 3～5 个，累计约 9～14）

**依赖：** 阶段 A 的目录与元数据。

**建议 Tool：**

| # | Tool（示例） | 说明 |
|---|--------------|------|
| 1 | `list_system_prompt_presets` | 读阶段 A 清单，支持按分类过滤。 |
| 2 | `apply_system_prompt_preset` | 按 id/标题应用到指定节点或全局策略（需定义语义）。 |
| 3 | `list_preset_templates` | 读模板目录。 |
| 4 | `merge_preset_template` | 调用现有「合并到画布」逻辑，参数模板 id 或名称。 |
| 5 | `search_assets`（可选） | 关键词检索预设/提示词，减少一次性塞进 prompt 的长度。 |

**验收：** 用户「用某某预设搭一个某某图工作流骨架」类话术可稳定完成。

---

### 阶段 E：工作流 / Comfy（本阶段新增约 4～8 个，累计约 13～22）

**依赖：** 节点侧工作流绑定、执行管线已文档化。

**建议 Tool（按你实际执行模型拆分）：**

| 类型 | 示例 |
|------|------|
| 查询 | `list_workflows_for_node`、`get_workflow_inputs` |
| 修改 | `bind_workflow`、`set_workflow_input` |
| 执行 | `run_workflow`、`get_run_status` |
| 结果 | `get_last_outputs_summary`（摘要避免爆 token） |

**验收：** 从「选工作流 → 改关键参数 → 跑 → 告知结果」全流程无需人手点（或仅危险步确认）。

---

### 阶段 F：风控与可观测（Tool：0 或 +1～3）

**目标：** 可上线试用，而不是 Demo。

**建议：**

- **确认类**：批量删除、覆盖工程、长时跑图 → `confirm_token` 或 UI 确认。  
- **限流**：单会话最大 tool 轮数、最大节点列出数。  
- **日志**：每轮 tool 入参出参摘要（脱敏）可导出。

可选 Tool：`export_session_trace`（仅调试环境）。

---

## 4. 与 OpenClaw / Skill 的衔接（后期）

当你 **阶段 C～D** 稳定后，若仍希望用 OpenClaw：

1. 把阶段 C～E 的 Tool **映射为 HTTP/CLI**（对外一个稳定 API）。  
2. 写 **Flowid SKILL.md**：只描述「何时调哪个 API、参数从哪来、失败怎么办」。  
3. 社区 Skill **不能**直接替你操作 Flowid，除非有人已为你的 API 写好适配（通常没有）。

**顺序建议：** 先 **应用内 Tools 全链路**，再 **外挂 Skill**，避免两套语义漂移。

## 5. 检查清单（开始写代码前自评）

- [ ] 系统提示词是否有 **稳定标题 + 描述 + 分类**，且可导出清单？  
- [ ] 预设模板是否 **名称不冲突、合并结果可预期**？  
- [ ] 是否已选定 **云端模型 + endpoint**，并验证 **tools/function calling**？  
- [ ] 是否已写 **10 条验收用例**（输入 + 预期画布变化）？  
- [ ] 是否接受 **多轮 tool**（对用户可做成「一条消息自动跑完」）？
